# AI Job Scavenger

Automatically discovers newly posted jobs from multiple sources, normalizes them with an LLM,
matches them to each user's preferences via keyword + semantic (embedding) similarity, and
notifies users through a desktop app.

> **Status: Increment 1 of N** — this delivers the production backend foundation: project
> structure, database schema, auth, preferences, the plugin-based scraper architecture (with
> RemoteOK + Greenhouse implemented), AI normalization, the two-stage match engine, the
> background scheduler/pipeline, Docker, and tests. The Electron/React desktop app is the next
> increment — see [Roadmap](#roadmap).

## Architecture

```
backend/app/
  api/routes/     REST endpoints (auth, profile, preferences, jobs, matches, saved, notifications)
  core/           config, logging, exceptions (cross-cutting concerns)
  database/       async SQLAlchemy engine/session
  models/         SQLAlchemy ORM models (profiles, preferences, jobs, matches, ...)
  schemas/        Pydantic request/response schemas
  services/       business logic (repository + service layer, one class per concern)
  scrapers/       plugin-based job source providers (base.py defines the contract)
  ai/             LLM provider abstraction (OpenAI/Gemini) + job normalization
  matcher/        two-stage match engine (keyword filter + embedding similarity)
  scheduler/      APScheduler wiring for periodic pipeline runs
```

### The ingestion pipeline

```
fetch jobs (scrapers) -> normalize (LLM) -> generate embeddings -> save (dedup)
    -> match every user's preferences -> store scored matches -> queue notifications
```

This whole sequence is `PipelineService.run_full_pipeline()` in
`app/services/pipeline_service.py`, invoked on a timer by `app/scheduler/jobs.py`
(default: every `SCRAPE_INTERVAL_HOURS`, configurable).

### Adding a new job source

1. Create `app/scrapers/<provider>.py`, subclass `BaseScraper`, implement `async fetch() -> list[RawJob]`.
2. Register the class in `app/scrapers/registry.py`'s `AVAILABLE_SCRAPERS` dict.
3. Nothing else changes — the pipeline discovers it automatically.

Implemented so far: **RemoteOK** (public JSON API) and **Greenhouse** (multi-tenant board API,
configured via `GREENHOUSE_BOARD_TOKENS`). Lever, Ashby, Wellfound, and generic career-page
scraping are stubbed as TODOs in the registry for the next increment.

### Matching

- **Stage 1 (keyword):** overlap ratio between a user's `skills` and a job's `required_skills`.
- **Stage 2 (semantic):** cosine similarity between the user's preference embedding and the
  job's embedding (both generated by the configured AI provider).
- Final score = `0.35 * keyword_score + 0.65 * semantic_score`, gated by hard filters
  (remote-only, location, salary floor, employment type) before scoring even runs.
- Every match stores a human-readable explanation, e.g.:

  ```
  Matched because (93% match):
  ✓ Python
  ✓ FastAPI
  ✓ Docker
  Missing:
  Redis
  ```

## Setup

### 1. Supabase project

1. Create a project at [supabase.com](https://supabase.com).
2. In the SQL editor, run `supabase/schema.sql` — this creates every table, the `pgvector`
   extension and index, row-level security policies, and a trigger that auto-creates a
   `profiles` row whenever someone signs up via Supabase Auth.
3. Grab your keys from **Project Settings → API** (URL, anon key, service role key, JWT secret)
   and your pooled connection string from **Project Settings → Database**.

### 2. Environment variables

```bash
cp .env.example .env
# fill in SUPABASE_*, DATABASE_URL, OPENAI_API_KEY, SECRET_KEY, etc.
```

### 3. Local development (no Docker)

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Visit `http://localhost:8000/docs` for interactive API docs (disabled automatically in production).

### 4. Local development (Docker)

```bash
docker compose up --build
```

This runs the API (`backend` service) and the scheduler (`worker` service) as separate
containers — the same topology used in production — pointed at your hosted Supabase Postgres.

### 5. Run tests

```bash
cd backend
pip install -r requirements.txt
pytest
```

## API overview

| Method | Path                              | Description                          |
|--------|------------------------------------|---------------------------------------|
| POST   | `/api/v1/auth/signup`             | Create account (delegates to Supabase Auth) |
| POST   | `/api/v1/auth/login`              | Login, returns JWT                    |
| POST   | `/api/v1/auth/logout`             | Logout                                |
| GET/PUT| `/api/v1/profile`                 | Get/update profile                    |
| GET/PUT| `/api/v1/preferences`             | Get/update job preferences (re-embeds on update) |
| GET    | `/api/v1/jobs`                    | List/search/filter jobs               |
| GET    | `/api/v1/jobs/{job_id}`           | Job detail                            |
| GET    | `/api/v1/matches`                 | This user's scored matches            |
| GET/POST | `/api/v1/saved`                 | List/save bookmarked jobs             |
| GET    | `/api/v1/notifications`           | Notification history                  |
| POST   | `/api/v1/notifications/{id}/read` | Mark a notification read              |

All endpoints except signup/login require `Authorization: Bearer <supabase-jwt>`.

## Production deployment (Railway / Render / DigitalOcean)

This app is two long-running services, both built from `docker/Dockerfile.backend` and
`docker/Dockerfile.worker`:

1. **API service** — `docker/Dockerfile.backend`, exposes port 8000, set
   `RUN_SCHEDULER_IN_PROCESS=false` and scale horizontally as needed.
2. **Worker service** — `docker/Dockerfile.worker`, runs `worker.py`, exactly **one** instance
   (it owns the scheduled pipeline run — running two would double-scrape and double-spend on AI calls).

Steps common to all three platforms:

1. Push this repo to GitHub.
2. Create the two services, pointing each at this repo with the respective Dockerfile
   (`docker/Dockerfile.backend` for API, `docker/Dockerfile.worker` for the worker).
3. Set all variables from `.env.example` as environment secrets on **both** services (never
   commit `.env`).
4. Point `DATABASE_URL` at Supabase's **connection pooler** (not the direct connection) for
   serverless-friendly connection handling.
5. Deploy. Confirm `GET /health` returns `{"status": "ok"}` on the API service.

For higher scrape/match throughput than APScheduler comfortably handles, swap
`app/scheduler/jobs.py` for Celery + Redis/RabbitMQ — `PipelineService` itself is
scheduler-agnostic and doesn't need to change.

## Security notes

- Passwords are never handled by this codebase — Supabase Auth owns signup/login/hashing.
- The backend verifies Supabase JWTs itself (`app/services/auth_service.py::decode_supabase_jwt`)
  rather than trusting client-provided identity.
- `SUPABASE_SERVICE_ROLE_KEY` must never reach the desktop client — it's backend-only.
- Row-level security is enabled on every user-scoped table in `supabase/schema.sql` as
  defense-in-depth, even though the FastAPI backend primarily connects with elevated privileges.
- All request bodies are validated via Pydantic; SQLAlchemy's parameterized queries prevent
  injection; CORS origins are explicitly allow-listed via `CORS_ORIGINS`.
